## Starting point

This is the only module with a branch switch. From the `app` directory, check out
fault 01 and rebuild with the observability overlay so the failure shows up in
telemetry:

```bash
git checkout fault/01-map-not-loading
docker compose --env-file .env.workshop \
  -f docker-compose.workshop.yml -f docker-compose.otel.yml up -d --build
```

(If you completed optional module 06b, fault 01 is already checked out — just make sure
the stack was rebuilt with the overlay.)

Budget about **20 minutes**.

Prerequisites: ClickStack telemetry (module 05) and your agent connected to the
ClickStack MCP with a dashboard and alert (module 06). If you completed optional module
06b, keep the LibreChat SRE agent open: this lab is where you use it against the fault
scenarios and verify the fixes.

## Why

This is the incident lab and the direct payoff from modules 06 and 06b. You inject a
realistic fault, then use everything you built — the telemetry, the dashboard, and your
MCP-connected editor or LibreChat agent — to find the root cause the way an on-call
engineer would, with the AI doing the heavy lifting.

## Goal

Diagnose the injected fault from telemetry alone, using your AI SRE, then apply the fix
and confirm the app recovers.

## Step 1 — Introduce the fault

### fault branch

The fault branch breaks one part of the app. Here is how you know the fault is active
(observable behavior only — the diagnosis is the exercise):

- `fault/01-map-not-loading` — the zone map stays empty while everything else works.

Check it out (see Starting point) and let the stack run long enough for the symptom to
surface in the dashboards and in ClickStack.

## Step 2 — Diagnose with the AI SRE

Use the editor agent from module 06 or the LibreChat SRE agent from optional module 06b,
then describe the symptom, not the cause:

```text
Something is wrong with the app: users are seeing errors. Using the clickstack MCP, investigate the traces and logs, localize the failure, and tell me the root cause with the evidence.
```


Then ask your own follow-up question about blast radius or timeline — this is your open
step.

Confirm the fault in the telemetry: open **Client Sessions** in the HyperDX sidebar and
pick your session. You will see the front-end `console.error`, the failed resource load,
and a replay of the empty map. The backend dashboard and alert can stay healthy because
this request never reaches FastAPI.

![ClickStack Client Sessions: an anonymous session flagged "1 Errors, 92 Events" with a highlighted console.error "ZoneMap: failed to load…" in the event timeline and a session-replay player showing the app with the broken map](/screenshots/07-client-session-error.png)

*ClickStack → Client Sessions records the browser errors and a replay of the user's session — proof the failure was captured, not just reproduced.*

## Step 3 — Apply the fix

### `backend/` or `frontend/`

Once you and the agent agree on the root cause, apply the fix (compare against `build-workshop-v1` if
you want the reference). Rebuild the affected service:

```bash
docker compose --env-file .env.workshop -f docker-compose.workshop.yml -f docker-compose.otel.yml up -d --build
```

You should see the symptom clear in the UI: the map loads again. Verify a fresh browser
session records no new `ZoneMap` error in Client Sessions; the backend signal is expected
to remain unchanged, because this fault never reached FastAPI.

## How to verify you are done

- The agent named the correct root cause and cited telemetry as evidence.
- After the fix, the map renders and a fresh browser session shows no new `ZoneMap` error
  in Client Sessions.

## Wrap-up

You just ran an incident end to end: detection, AI-assisted diagnosis from telemetry,
and remediation — on a system you built during the same session.

## End state

The incident is resolved. Preserve your fix for later comparison, return to the complete
base app, and rebuild it with telemetry still enabled:

```bash
git stash push --include-untracked -m "module-07-fix"
git switch build-workshop-v1
docker compose --env-file .env.workshop \
  -f docker-compose.workshop.yml -f docker-compose.otel.yml up -d --build
```

`git stash push` is safe when there is nothing to save; Git simply reports that there are
no local changes. Continue to [08 Chat and Langfuse](/docs/learner/08-chat-langfuse) to
wire and trace the in-app AI experience.
