title: 03 Real-time CDC
description: Create your own Postgres managed by ClickHouse, stream its rows into ClickHouse with a Postgres CDC ClickPipe, and watch the Ops dashboard go live.

## Starting point

You are on `build-workshop-v1` — no checkout needed. Budget about **20 minutes**.

Prerequisites: module 02 complete (Cloud service seeded, back end reading from
ClickHouse), and the organization API key you created in module 00.

## Why

The Ops dashboard needs fresh data. Rather than build a bespoke pipeline, you use a
Postgres CDC ClickPipe: it reads the write-ahead log of a Postgres database and
replicates changes into ClickHouse continuously. Your dashboard goes from static to live
without any custom ingestion code.

You provision that Postgres yourself, in your own trial org, with `clickhousectl` — a
**Postgres managed by ClickHouse** instance. That keeps your Postgres and your ClickPipe
in the same organization, and every managed instance ships CDC-ready
(`wal_level=logical` with replication slots to spare), so there is nothing to configure
before the pipe can read it.

## Goal

Your own managed Postgres instance receiving synthetic trips from the data generator,
and a running Postgres CDC ClickPipe replicating that stream into your ClickHouse Cloud
service, with the Ops dashboard updating live.

## Step 1 — Create your own Postgres managed by ClickHouse

From the directory where you run `clickhousectl` (the same one you logged in from in
module 00 — the org API key authenticates this), create a managed Postgres instance.
Use the **same region as your ClickHouse Cloud service** so the pipe stays in-region:

```bash
clickhousectl cloud postgres create \
  --name my-workshop-pg \
  --region us-east-1 \
  --size m8gd.large \
  --pg-version 17 \
  --ha-type none
```

Set `--region` to your ClickHouse service's region. The command returns JSON; two fields
matter, and the password is shown **only once**:

- the instance **hostname** (ends in `...pg.clickhouse.cloud`)
- the **one-time admin password** for the `postgres` user

Copy both somewhere safe right now.

<Callout type="warn" title="If you lose the one-time password">
  It is never shown again. Reset it with
  `clickhousectl cloud postgres reset-password <service-id>` and use the new one. Do not
  rely on `postgres get`/`list` to read it back — those beta status APIs can return empty
  or FORBIDDEN even while the instance itself is healthy.
</Callout>

## Step 2 — Point the data generator at your instance

The workshop stack already includes `pg-trip-writer`, the data generator. Put your
instance's values into `.env.workshop` (in the `app` directory):

```bash
PGHOST=<hostname from the create output>
PGPORT=5432
PGDATABASE=postgres
PGUSER=postgres
PGPASSWORD=<one-time password from the create output>
PGSSLMODE=require
PG_PUBLICATION=pub_taxi
```

Then restart just the generator and watch its log:

```bash
docker compose --env-file .env.workshop -f docker-compose.workshop.yml up -d pg-trip-writer
docker compose --env-file .env.workshop -f docker-compose.workshop.yml logs -f pg-trip-writer
```

**The log is your readiness check** — you do not poll any status API. A new instance
accepts connections within about a minute; until it does, the generator container exits
and restarts automatically, so a connection error or two at the start is normal. When the
instance is up you will see, in order:

```
[loadgen] connecting: ...pg.clickhouse.cloud:5432 db=postgres user=postgres
[loadgen] ensured realtime_trips table exists
[loadgen] created publication pub_taxi for public.realtime_trips
[loadgen] inserted 10 trips @ ...
```

Because you connect as the instance admin, the generator creates the `realtime_trips`
table **and** the `pub_taxi` publication for you — no `psql` needed. Once you see rows
being inserted, your Postgres is live and ready for a ClickPipe.

## Step 3 — Create the Postgres CDC ClickPipe

In the ClickHouse Cloud console, go to **Data Sources -> Set up a ClickPipe ->
Postgres CDC**. Fill the connection step with your instance's values and select the
source in the replication step:

- Host: your `PGHOST`   Port: `5432`   Database: `postgres`
- User: `postgres`   Password: the one-time password
- Publication: `pub_taxi`
- Table: `public.realtime_trips`

<Callout title="chctl alternative">
  You can also create the pipe from the command line against your ClickHouse service id:

  ```bash
  clickhousectl cloud clickpipe create postgres <your-clickhouse-service-id> \
    --name taxi-cdc --host "$PGHOST" --port 5432 \
    --pg-database postgres --username postgres --password '<one-time password>' \
    --publication-name pub_taxi \
    --replication-mode cdc \
    --table-mapping "public.realtime_trips:realtime_trips"
  ```

  Prefer the console wizard: a CLI-created pipe lands its destination table in the
  `default` database (the `--table-mapping` target does not accept a database qualifier),
  whereas the wizard lets you pin the destination to `nyc_tlc_data` in the next step.
</Callout>

## Step 4 — Accept the destination mapping

The wizard auto-creates the destination table as
`ENGINE = ReplacingMergeTree(_peerdb_version)` with `_peerdb_synced_at`,
`_peerdb_is_deleted`, and `_peerdb_version` bookkeeping columns. Pin the destination to
database `nyc_tlc_data` and keep the source table name, which yields
`nyc_tlc_data.realtime_trips`.

### `db/cloud/003_cdc_mv.sql`

After the ClickPipe's initial snapshot creates `realtime_trips`, confirm the column
types and run the CDC materialized view that feeds `taxi_trips`:

```sql
DESCRIBE nyc_tlc_data.realtime_trips;   -- expect the PeerDB mapping:
                                        --   timestamptz     -> DateTime64(6)
                                        --   int2/int4/int8  -> Int16/Int32/Int64
-- Then run db/cloud/003_cdc_mv.sql. It creates realtime_trips_to_taxi_trips_mv, which
-- selects from realtime_trips into taxi_trips WHERE _peerdb_is_deleted = 0. An MV fires
-- per inserted block, so no FINAL is needed; the loadgen is append-only, so no version
-- churn occurs.
```

If you created the pipe with the CLI alternative (Step 3), its destination table is
`default.realtime_trips` rather than `nyc_tlc_data.realtime_trips`; `003_cdc_mv.sql`
includes a variant for that source, so run the one matching the table the pipe created.

## Step 5 — Watch the Ops dashboard go live

Open the Ops dashboard at `http://localhost:8080/` and watch counts move as new trips
flow Postgres -> ClickPipe -> ClickHouse -> dashboard.

<Callout type="warn" title="Fallback: no managed Postgres in your org">
  Managed Postgres is in beta and availability varies by org. If
  `clickhousectl cloud postgres create` is not available to you, your instructor hands out
  a shared-Postgres slip. Use its values in the **same** `.env.workshop` and ClickPipe
  fields — `PGHOST`, `PGDATABASE` (named `taxi_pNN`), `PGUSER`, `PGPASSWORD`,
  `PGSSLMODE=require`, and set `PG_PUBLICATION` to the slip's publication (`pub_taxi_pNN`).
  On the shared instance the table and publication are pre-created for you, so the
  generator log shows `publication ... already exists` instead of creating one — that is
  expected. Everything else in this module is identical.
</Callout>

## How to verify you are done

- The generator log shows your managed instance reachable and the publication ready
  (`created publication pub_taxi` on your own instance, or `already exists` on the shared
  fallback), followed by `inserted N trips`.
- The ClickPipe shows an active, replicating state in the console.
- The destination table row count in ClickHouse increases over time.
- The Ops dashboard updates without a manual refresh.

## Wrap-up

You now have both halves of the data plane on ClickHouse: seeded history from module 02
and a live CDC stream from this module, sourced from a Postgres you provisioned yourself
in the same org. The app is fully backed by ClickHouse Cloud.
