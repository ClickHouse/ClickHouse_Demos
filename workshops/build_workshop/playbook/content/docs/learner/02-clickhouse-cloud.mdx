## Starting point

You are on `build-workshop-v1` — no checkout needed. Budget about **15 minutes**.

Prerequisites: your ClickHouse Cloud service created and its host and password in
`.env.workshop` (module 00).

## Why

The app has no analytics data yet — module 01 was a tour of an empty UI. In this module
you give it a real warehouse: create the taxi schema on ClickHouse Cloud, seed it with
historical trip data, and point the back end at it. This is where the dashboards first
light up.

## Goal

A running ClickHouse Cloud service with the taxi schema created and seeded with
historical trip data, and the app's back end reading from it.

## Step 1 — Confirm your service and credentials

You created the Cloud service in module 00, so it already exists and its host and password
are in `.env.workshop`. Confirm the `CLICKHOUSE_*` block is filled in - `CLICKHOUSE_HOST`
is the bare hostname (no scheme, no port), and the credentials come from the service's
**Connect** modal (left-nav **Connect** button) if you need to re-copy them:

```bash
CLICKHOUSE_HOST=<your-service>.<region>.<cloud>.clickhouse.cloud
CLICKHOUSE_PORT=8443
CLICKHOUSE_USER=default
CLICKHOUSE_PASSWORD=<from the service's Connect modal>
CLICKHOUSE_DATABASE=nyc_tlc_data
CLICKHOUSE_SECURE=true
```

## Step 2 — Create the schema

### `db/cloud/001_cloud_schema.sql`

The workshop ships an idempotent schema file. First create the destination database,
then run the schema against your service (Cloud SQL console, `clickhousectl`, or your
agent):

```sql
CREATE DATABASE IF NOT EXISTS nyc_tlc_data;
-- then run db/cloud/001_cloud_schema.sql, which creates the base objects:
--   taxi_zones, fhv_trips, taxi_trips           (ENGINE = MergeTree; Cloud backs these
--                                                 with SharedMergeTree transparently, so
--                                                 no ON CLUSTER / Replicated* is needed)
--   taxi_trips_expanded, fhv_trips_expanded     (enrichment views)
```

<Callout>
  `001_cloud_schema.sql` creates only the base tables and views, and runs cleanly on its
  own. The CDC materialized view that feeds `taxi_trips` is added in module 03 (from
  `db/cloud/003_cdc_mv.sql`), once the ClickPipe exists.
</Callout>

## Step 3 — Seed historical data from object storage

### `db/cloud/002_seed_historical.sql`

The workshop ships a runnable seed file — no uncommenting, no local import step. It loads
`taxi_zones` from the public TLC zone-lookup CSV and a month of yellow-taxi trips from the
public TLC parquet exports, straight from object storage. Run it once against your service,
after the schema file:

```bash
clickhouse client --host <your-service>.<region>.<cloud>.clickhouse.cloud --port 9440 --secure \
  --user default --password '<password>' --multiquery < db/cloud/002_seed_historical.sql
```

Or paste both statements into the Cloud SQL console (zones first, then trips). Both are
idempotent — each is guarded by a `count() = 0` check — so re-running the file cannot
double-load. To add more months, copy the second statement with the next month's file name
(each month is ~3M rows, so keep it small for a workshop service).

This gives the Historical dashboard real volume.

## Step 4 — Point the back end at ClickHouse

### `docker-compose.workshop.yml`

The workshop back end is already env-driven — no code change is required. Pointing it at
Cloud is just supplying the `CLICKHOUSE_*` values in `.env.workshop` and (re)starting the
workshop stack:

```bash
docker compose --env-file .env.workshop -f docker-compose.workshop.yml up -d
```

(The back end infers TLS from `CLICKHOUSE_PORT=8443`, and `CLICKHOUSE_SECURE=true` makes
it explicit. It also allows a longer first-connect timeout because a Cloud service can
idle-scale to zero and take a few seconds to wake.)

## Step 5 — Feel the query speed

Open the Historical dashboard. Now that ClickHouse Cloud is seeded, the charts render —
try a wide date range and watch the seeded historical data (a few million rows) come back
in well under a second. Then ask your agent your own analytical question against the
data — this is your open step.

## How to verify you are done

- Your Cloud service lists the taxi tables with rows in them.
- The Historical dashboard now renders from ClickHouse, returning wide-range queries in
  well under a second.
- Your own analytical question returns a sensible answer.

## Wrap-up

The historical analytics workload now runs on ClickHouse Cloud, seeded directly from
object storage. What is still missing is fresh data: the Ops dashboard is not live yet.

## End state

Historical data is on ClickHouse and the back end reads from it. Continue to
[03 Real-time CDC](/docs/learner/03-realtime-cdc) to stream live rows in.
